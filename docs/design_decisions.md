# Zero-TTT 设计决策

本文件记录当前项目中已经接受、会长期影响实现的选择。早期快记忆方案的 D-001 至 D-011 已完整保存在[历史归档](archive/fast-memory-2026/design_decisions.md)中，因此当前编号从 D-012 继续。

状态取值：`已接受`、`试验中`、`已取代`、`已撤销`。如果决定被替代，应保留原记录并链接新决定，不能静默改写历史。

## D-012：近期转向 AlphaZero 风格围棋工程

- **日期：** 2026-08-17
- **状态：** 已接受
- **决定：** Zero-TTT 近期以个人学习、实践和娱乐为目的，完成可训练、可自博弈、可通过 GTP 对弈的 AlphaZero 风格围棋系统。
- **理由：** 原快记忆方案同时包含围棋基础设施、MCTS、在线参数记忆和元学习，首个闭环过深；先获得可玩的可靠底座更适合个人长期推进。
- **影响：** 项目不承诺严格复现、论文结论、排行榜成绩或指定棋力。

## D-013：正式目标只支持 19×19 围棋

- **日期：** 2026-08-17
- **状态：** 已接受
- **决定：** 第一条正式产品路线固定为标准 19×19 棋盘，不以 5×5、9×9 或其他游戏作为前置成果。
- **理由：** 项目的实际兴趣是标准围棋；小棋盘训练结果不能代表最终想玩的系统。
- **影响：** 单元测试仍可构造局部形状和极小样本，但公开配置、数据过滤、动作空间和 GTP 第一版都围绕 19×19 设计。

## D-014：允许使用开源棋谱预训练

- **日期：** 2026-08-17
- **状态：** 已接受
- **决定：** 自博弈强化学习前允许使用许可清晰的开源棋谱预训练，数据可以来自人类对局或程序自博弈。
- **理由：** 预训练可以降低个人算力下的冷启动成本，也能练习完整的数据工程流程。
- **影响：** 项目称为“AlphaZero 风格”而非严格从零复现；数据适配器必须同时容纳普通 SGF 和带搜索监督的富自博弈记录。

## D-015：富搜索目标优先于实战落子目标

- **日期：** 2026-08-17
- **状态：** 已接受
- **决定：** 数据提供有效的 MCTS 根访问分布时，使用其作为策略监督；只有实际落子时，退化为 one-hot 策略目标。价值统一转换为当前行棋方视角。
- **理由：** 访问分布表达搜索对多个候选动作的判断，比单个最终落子包含更多信息，同时普通 SGF 仍可使用。
- **影响：** 统一样本需要标记目标类型、数据来源和可用的搜索元数据。

## D-016：基线与点子实验分离

- **日期：** 2026-08-17
- **状态：** 已取代
- **决定：** 标准 AlphaZero 风格路径必须在不启用实验机制时独立运行；三速权重等想法通过可关闭的训练策略边界接入。
- **理由：** 项目允许频繁试错，但仍需要一个能定位规则、数据、搜索和训练问题的稳定底座。
- **影响：** 未经验证的想法写入 `ideas.md`，不能直接改写基础环境或 MCTS 的正确性语义。2026-08-18 起，三权重例子由 D-021 的双权重主线取代，基线隔离原则由 D-023 继续规定。

## D-017：通过 GTP v2 提供首个可玩接口

- **日期：** 2026-08-17
- **状态：** 已接受
- **决定：** 第一版人工对弈使用 GTP v2，不自制网页棋盘。
- **理由：** GTP 能直接接入现有棋盘软件，把有限精力集中到算法和训练流程。
- **影响：** 围棋环境必须支持外部落子、清空、贴目、悔棋、终局计分和确定性状态恢复。

## D-018：数据必须具备可追踪的许可与版本

- **日期：** 2026-08-17
- **状态：** 已接受
- **决定：** 正式训练数据必须记录来源、许可、具体文件或版本、校验值、解析格式和过滤统计；不使用许可不清晰的抓取数据。
- **理由：** 能下载不等于可以稳定使用，可追踪的数据清单也是实验可恢复性的一部分。
- **影响：** KataGo g104 等 CC0 档案是候选而非硬编码依赖；更换数据源不需要修改模型核心接口。

## D-019：旧快记忆研究完整归档

- **日期：** 2026-08-17
- **状态：** 已接受
- **决定：** 旧研究设计、PDF、实施计划和 D-001 至 D-011 移入 `docs/archive/fast-memory-2026/`，内容保持原貌。
- **理由：** 当前转向不应抹掉已经形成的思考，未来也可能在 AlphaZero 基线之上重新探索。
- **影响：** `third_party` 中三个 TTT 参考子模块保留原路径，但不作为当前主线依赖。

## D-020：取消竞技评估与模型晋升门控

- **日期：** 2026-08-18
- **状态：** 已接受
- **决定：** 当前训练闭环不运行候选模型与冠军模型之间的独立对局，不设置胜率晋升门槛，也不因验证指标下降自动回退权重。验证损失、固定局面回归、数值健康检查和故障 checkpoint 继续保留，但只负责观测与停止错误运行。
- **理由：** 竞技评估会持续占用个人 GPU 搜索预算，而本项目现阶段更需要把算力用于预训练、自博弈数据和主线正确性。低成本诊断足以暴露明显退化，不需要成为训练门锁。
- **影响：** 删除 `candidate`、`champion`、竞技对局和晋升状态；模型版本按发布顺序递增。非有限值会停训，但普通指标退化只记录，不触发自动恢复。

## D-021：训练与产数采用 `fast`/`slow` 双权重

- **日期：** 2026-08-18
- **状态：** 已接受
- **决定：** `fast` 接受正常梯度更新，`slow` 通过以样本数定义的 EMA 跟随；自博弈、GTP 和发布只使用不可变的 `slow` 快照。默认 EMA 半衰期为 1,048,576 个训练样本，每 16 个优化器步骤做一次等效更新，每 256 步发布一次。
- **理由：** `fast` 保持学习响应速度，`slow` 平滑短期梯度噪声；稀疏等效 EMA 减少逐步复制大模型的带宽成本，同时不需要第三份锚点权重或竞技评估。
- **影响：** I-001 的三权重方案被本决定取代；checkpoint 必须明确保存 `fast`、FP32 `slow`、样本计数和 EMA 状态。一次 MCTS 和一盘自博弈中不得切换模型版本。

## D-022：以约 3 亿参数的棋盘 Transformer 为默认模型

- **日期：** 2026-08-18
- **状态：** 已接受
- **决定：** RTX 4090 Laptop 16 GB 默认档使用 24 层、`d_model=1024`、16 头、SwiGLU `d_ff=2816` 的 Transformer Encoder，以 361 个棋盘 token、一个全局 token 和 2D RoPE 建模。主体使用 Pre-RMSNorm、QK-Norm、零 dropout、PyTorch SDPA、BF16、`torch.compile` 和 activation checkpoint。
- **理由：** 预训练数据可以降低大模型自博弈冷启动压力；短而固定的 362 token 序列适合使用较宽的 Transformer，并能利用当前 Ada GPU 的注意力内核。零 dropout 简化 checkpoint 重计算和编译图的随机状态。
- **影响：** 基础模型约 3.09 亿参数，物理 batch 固定为 16，默认梯度积累 16 步。最终编译训练图的峰值保留显存不得超过 14.5 GiB；超限时增加 checkpoint 覆盖率而不缩小模型。

## D-023：配置文件是参数事实来源，工程加速与算法优化分开记录

- **日期：** 2026-08-18
- **状态：** 已接受
- **决定：** 一次运行的模型、训练、搜索、回放和实验参数只从一个版本化 TOML 文件读取，不接受命令行或环境变量逐项覆盖。标准路径必须在关闭实验分支时独立运行。精确缓存、批处理、SDPA、编译和 checkpoint 归为工程加速；虚拟损失、根噪声、FPU、动态预算、滑动回放、增强和辅助损失归为会改变运行行为的算法优化。
- **理由：** 单一、严格且可哈希的配置能够复现大模型训练；分开两类优化可以避免把浮点近似或搜索启发式错误描述为“完全无损”。
- **影响：** checkpoint 内嵌规范化配置、schema 版本和 SHA-256。算法优化的实际参数与随机状态必须随 checkpoint 保存，并由独立测试覆盖；具体默认值集中在 `model_search_design.md`。
